# Phase 1 Research: IPC Discernment

## Scope and provenance

- **[USER]** Goal: intercept incoming tasks and distinguish casual chat from actionable workflows.
- **[USER]** Requirement: `CHAT-01`.
- **[USER]** Acceptance examples: `hello` uses casual response mode and bypasses full execution; `make a new button` uses the full actionable workflow.
- **[USER]** Constraints: Laravel monolith with React/Inertia and Node CommonJS orchestration in `.agents`; no package installation; never read `.env`, `.npmrc`, credentials, or key files; respect project planning documents.
- **[REPO]** Governing roadmap and requirement files are under `.planning/ROADMAP.md` and `.planning/REQUIREMENTS.md`; no root-level copies exist.
- **[REPO]** No `CONTEXT.md` exists for this phase. Existing generated context is represented by `ARCHITECTURE.md` and `.agents/architecture_map.json`.
- **[REPO]** No external/official documentation was needed; findings below come from current repository source and project documents.

## Current architecture and concrete seams

The browser page `resources/js/Pages/Brains/JarvisUI.tsx` posts every non-empty submission to `/api/brain/dispatch`. `routes/web.php` and `routes/api.php` route that request to `App\\Http\\Controllers\\TaskDispatcherController::dispatch()`.

`TaskDispatcherController::dispatch()` currently validates a string, selects a model using `analyzeTaskComplexity()`, optionally persists image attachments, appends a payload to `.agents/task_queue.json`, writes `.agents/pending_task.json` for immediate pickup, persists USER and SYSTEM messages, and returns success. There is no casual-chat branch; therefore `hello` currently enters the same queue path as a code request.

`.agents/task_watcher.cjs` consumes the queue FIFO-first, falls back to `.agents/pending_task.json`, clears the pending payload, sets `.agents/speaking.lock`, and posts `brain-status` to Laravel. It does not classify tasks, so classification must happen before queue insertion or at a clearly defined watcher boundary.

`.agents/AGENTS.md` defines the intended behavior: actionable input gets the full thought-stream/execution sequence; casual input uses `stream_thoughts.js` with `NONE` as lead brain, and skips `finish_task.js` and `speak.cjs`. `.agents/stream_thoughts.js` already resets all brains to `idle` when `NONE` is present.

The UI receives orchestration events through `/webhook/brain-status` and `/webhook/brain-message` in `routes/web.php`, which broadcast status/message events and persist brain messages. `speak.cjs` and `finish_task.js` are CommonJS-compatible operational helpers despite the repository root declaring ESM (`package.json`); `.cjs` is the safe extension for new Node modules that use `require`.

## Recommended architecture pattern

Introduce one deterministic, side-effect-free discernment seam close to the ingress boundary, preferably a small PHP service or private controller method used before model selection, attachment persistence, queue writes, and SYSTEM acknowledgment. Its result should be an explicit enum-like value such as `casual` or `actionable`, carried in the request flow rather than inferred later from queue contents.

Suggested flow:

1. Normalize only for classification (trim, Unicode-aware lowercase, collapse repeated whitespace); preserve the original user text for display and storage.
2. Classify obvious casual utterances such as greetings and lightweight conversational phrases as `casual`.
3. Treat imperative/change-oriented requests such as `make a new button` as `actionable`.
4. For casual input, do not append queue/pending files, do not invoke the task watcher execution path, and broadcast one appropriate casual response through the existing brain-message/status contract. Use the existing `stream_thoughts.js ... NONE` contract if the response is generated by Node.
5. For actionable input, preserve the current queue payload and watcher lifecycle unchanged, then let the existing full workflow run.
6. Return a response that identifies the mode (`casual` or `actionable`) so integration tests can assert routing without relying only on timing or UI state.

Keep classification conservative: unknown, mixed, or ambiguous requests should default to `actionable` or an explicit clarification path, never silently disappear. The classifier should be pure and independently testable with table-driven cases for `hello`, whitespace/case variants, `make a new button`, ordinary questions, empty input, and mixed text.

## Pitfalls and edge cases

- Classifying after queue insertion still causes the watcher to observe the message, violating the casual bypass requirement.
- `TaskDispatcherController` currently logs and acknowledges every dispatch; casual mode must avoid misleading “Task Received” workflow messaging.
- Queue and pending files can diverge: the watcher checks the queue first and then pending. Casual messages must not be written to either file.
- `fs.watch` and direct JSON rewrites can produce repeated events; do not create a second watcher or depend on one notification per task.
- `task_watcher.cjs` uses timestamps for deduplication, while queue entries are consumed FIFO. Preserve timestamps and payload shape for actionable tasks.
- Case, punctuation, whitespace, multilingual greetings, and short questions can defeat a brittle exact-match list. Normalize classification input and test boundaries.
- Over-broad keyword rules can misclassify conversational requests (“can you tell me how to make a new button?”) or task nouns without an action. Prefer intent cues plus a safe actionable default.
- Empty text with images is currently accepted by the UI/controller contract. Decide explicitly whether attachments make a request actionable; do not let classification accidentally bypass attachment handling.
- Root `package.json` has `"type": "module"`; new Node code using `require` must be `.cjs` or use imports consistently.
- Do not use `finish_task.js` for casual mode; the repository’s own protocol says this can create an incorrect completion narrative and race with `stream_thoughts.js`.

## Security and threat considerations

- **Prompt/content injection:** User text is untrusted input. Classification must be structural and bounded; never execute user text as a shell command or interpolate it into a command line.
- **Workflow bypass:** A classifier that defaults casual too aggressively can suppress requested code changes. Fail closed to actionable for uncertain input and preserve the original task text.
- **Queue integrity:** Use Laravel-controlled serialization and atomic/consistent file writes where possible; never allow classification metadata from the client to select the mode.
- **Webhook trust:** Existing local webhooks validate shape but do not authenticate callers. Do not expand their trust boundary or accept a client-provided “casual” flag as authoritative.
- **Denial of service:** Bound input length before normalization/classification and avoid expensive model calls for the classifier. Existing request validation only requires `string`; phase implementation should consider a practical max length without breaking the established contract.
- **Sensitive data:** Do not log more user content than the existing behavior requires. Attachments and task text may contain sensitive material; classification responses should not echo raw content unnecessarily.
- **Race conditions:** Keep casual handling out of queue files and avoid concurrent writes to `speaking.lock`; reuse the existing stream lock/status behavior.
- **Output safety:** Casual responses derived from user text must be encoded through the existing webhook/database/UI path; do not emit executable markup or shell fragments.

## Verification targets for CHAT-01

At minimum, verify the following observable contract at the dispatch boundary:

| Input | Expected mode | Queue/pending write | Full workflow |
|---|---|---:|---:|
| `hello` | casual | no | bypassed |
| `HELLO!` | casual | no | bypassed |
| `make a new button` | actionable | yes | runs |
| ambiguous/mixed request | actionable or explicit clarification | no silent drop | must not be silently bypassed |

Concrete files likely involved in implementation/tests: `app/Http/Controllers/TaskDispatcherController.php`, a new classifier/service under `app/Services/` if extracted, `routes/api.php` and/or `routes/web.php` only if response routing changes, `.agents/stream_thoughts.js` only if casual response integration needs a contract adjustment, and feature/unit tests under `tests/Feature/` or `tests/Unit/`. Do not modify the Laravel/Inertia base architecture.

## Research conclusion

The smallest coherent Phase 1 change is an ingress classifier with an explicit mode result and a casual branch before queue/file side effects. Existing Node streaming infrastructure already supports the required casual reset (`NONE`), while the actionable path can retain the current watcher and queue behavior. The main implementation risk is false casual classification; defaulting uncertain input to actionable and testing both positive acceptance examples directly addresses CHAT-01.
